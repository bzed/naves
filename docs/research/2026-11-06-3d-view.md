# What a real 3D view takes

Date: 2026-11-06. Status: result of a spike. The code is on the branch `spike/3d-view` (commit `2bb62cc`), which is **not
merged**; this note is. It answers whether the promise of the editor shell's plan (*2D and 3D*: "everything outside a
viewport speaks map metres, so that a 3D view is one more `impl Viewport`") holds, before the houses plan relies on it.

**Short answer: it holds.** The shell needed no change for the 3D view to work with the stack, the band, the status
line, the selection, the problem markers, the empty states and Ctrl+Tab. The spike found two rules that each view
had to repeat (wheel direction, panning), which are now shared in the merged code, and one cost the plan did not
mention (the drape's opacity), described below.

## 1. Swapping the backend

`eframe` gets the feature `wgpu` instead of `glow`; `run` asks for `Renderer::Wgpu` and `depth_buffer: 24` (the
terrain needs a depth test, and the depth attachment belongs to egui's one render pass). That is the whole swap.
The GUI looks and behaves the same; the screenshots of the spike on the Königssee fixtures differ from glow's
in nothing but the 3D view.

| | glow (the merged code) | wgpu (the spike) |
|---|---|---|
| `make deny` (`cargo deny check`) | ok | ok: advisories, bans, licences and sources pass; 22 duplicate-version warnings against 20 |
| crates in the build (`cargo tree -e normal`, unique) | 297 | 337 (+40, `wgpu` 30.0.1, `egui-wgpu`, `naves-*` unchanged) |
| clean release build, 8 cores | 34 s | 37 s |
| release binary | 24.7 MB | 31.8 MB (+7.1 MB, +29 %) |
| libraries the binary links | libc, libm, libgcc | the same: Vulkan, GL, Wayland and X11 are loaded at run time |
| `naves gui` starts | yes | yes: Vulkan on the maintainer's machine (the AMD driver `radv`), also inside a headless sway |
| `egui_kittest` | 194 tests | 199 tests (194 + 5 of the spike) pass unchanged: the paint callback is built and not run |

Two things to know:

- **Colour space.** egui draws into a surface that is not sRGB. A texture made as `Rgba8UnormSrgb` is decoded to linear and
  comes out too dark (the relief's mid grey 180 showed as 120). The draped picture must be `Rgba8Unorm`, the
  same bytes the 2D view uploads.
- **`unsafe`.** The spike has none. `egui_wgpu::CallbackTrait` and `wgpu` are safe APIs; `glow`'s are `unsafe fn`
  throughout, so the 3D view could not have been written on the current backend with `unsafe_code = "forbid"`.

## 2. The `TerrainViewport`

About 450 lines (`gui/viewport/terrain.rs`): a grid mesh of the heightmap (at most 256 × 256 vertices), a WGSL shader, an
orbit camera (left drag orbits, middle drag pans, the wheel zooms), and the base map with the visible layers drawn
over it by `render_topdown` and `render_layer` for the whole map, put together on the CPU into one 1024 × 1024 texture.

What the expected trouble turned out to be:

- **`CallbackTrait` is `Send + Sync`.** No trouble: the callback holds plain data (the view-projection matrix and
  what is to be uploaded). Everything on the GPU lives in egui's `CallbackResources`, created on first use in `prepare`,
  which is given the device.
- **GPU resources come from the creation context.** Only two values do: the surface format and the depth format,
  needed to build the pipeline. `TerrainViewport::new(format, depth_bits)` takes them, and `run` calls it from the
  `eframe` creation closure. So `default_views()` can no longer be a function without arguments: it becomes
  `default_views(gpu: Option<GpuInfo>)` (the map alone without a GPU). `NavesApp::with_views` is `#[cfg(test)]` today and has
  to become a normal method.

## 3. The seam, walked

With real data (`gui/tests/spike3d.rs`, on the branch):

| Question | Result |
|---|---|
| Ctrl+Tab there and back keeps the place | **Yes.** The map's focus is the 3D camera's target and distance, and back. `set_focus` before the first `show` is honoured, as the trait says. |
| Too steep to walk is draped; H, Shift+H and fading work | **Yes, with a cost.** `VisibleLayer` carries all a view needs. But the spike bakes each layer's opacity into the one draped picture, so every H, Shift+H or level change makes the picture again (the test shows `renders` going up, where the map's stays put). The shell promises that switching renders nothing; **a real 3D view keeps one texture per layer and blends them in the fragment shader with the opacities as uniforms.** |
| A problem marker and the selection ring sit on the ground through `project`, and vanish behind the camera | **Yes.** `project` puts the point on the ground (plus 2 m) through the same matrix as the mesh and gives `None` behind the camera or outside the view. |
| A click gives the same `Selection` as on the map | **Yes.** The view marches a ray along the heightmap in `show` and reports `ViewEvent::Click` in map metres; the middle of the screen is where the camera looks, and the selection there is the terrain's, with its height row. |
| Level, band and status line do not notice | **Yes.** They are drawn by the shell. |
| Empty states stay in the shell | **Yes.** The shell does not call `show` without data, in either view. |
| The wheel is the view's own | **Yes**, with the shared rule below. |

What a view needs that a level or tool assumes about a top-down picture:

- **Two rules were repeated in the view and then forgotten.** The spike's 3D view ignored the *Invert the zoom direction*
  setting and the rule that Space with a left drag pans. Both are now shared in the merged code
  (`viewport::zoom_factor` and `viewport::pans`, with tests), so a second view cannot forget them by accident.
- **A click is a point on the ground.** `ViewEvent::Click { at }` has no height. For terrain that is exact. For objects
  (houses, a bridge over a road, a second floor) the same `(x, y)` has several things above it, and a view that picks
  meshes knows which one was hit. The houses plan has to extend the event, for instance with the ray or the height of
  the hit, before `LevelDef.pick` can choose among them. Nothing else in the shell assumes a point is enough.
- **Drag tools need a hit on every event.** A brush dragged across the horizon has no hit. The view drops such events;
  the tools already treat the events as a sequence of points in metres.
- **`ViewFocus.span_m`** is defined as the metres covered by the shorter side of a top-down view. In 3D the spike maps
  it through the field of view at the target's distance. That works for Ctrl+Tab and for Frame selection; it is not the
  size of what the camera sees, and nothing may use it as such.
- **The hatching is in image pixels, and is draped.** At 1024 px over 750 m it reads well on the mesh. On the 6.4 km map
  of the Berchtesgaden example one pixel is 6 m, and hatching that is 6 px apart on the picture is 36 m apart on the
  ground. A 3D view that wants it finer renders `render_layer` for the part it looks at, not the whole map.

## 4. What the MCP's "3D view from a given camera" (spec 5.10) needs on top

The AI sees what the user sees. For a camera it needs the renderer without a window:

- **Split the scene from the egui callback.** The mesh, the pipeline and the camera become a `TerrainScene` that can draw into any
  `wgpu::TextureView`. The egui callback draws it into the window's pass, the MCP tool into an offscreen texture.
- **Offscreen path.** `wgpu::Instance` and `request_adapter` with no surface; draw into a `Texture` with
  `RENDER_ATTACHMENT | COPY_SRC`; `copy_texture_to_buffer`, map the buffer and wait for it; encode the PNG as the
  `render_topdown` tool does. The MCP server is async, so this runs in `spawn_blocking`.
- **Machines without a GPU.** `naves mcp` and `naves build` still start (the binary links no GPU library; the
  loaders are opened at run time), but the 3D tool then has no adapter and must say so as a tool error. Tests for it
  are `#[ignore = "needs a Vulkan device"]`, with the faked path (a trait seam over the renderer) in the normal run. In CI a software
  Vulkan driver (`mesa-vulkan-drivers`, lavapipe) would let them run; that is an option, not a promise.
- The camera of the tool is the same `Camera` the view has, with `ViewFocus` as its shared description.

## 5. What the houses plan has to do

1. Switch the backend in its first task: the `wgpu` feature, `Renderer::Wgpu`, `depth_buffer`, and the `deny` run.
2. Make the view's drape per layer (one texture each, blended in the shader).
3. Draw models: P3D meshes, instanced, with the picking above (the ray, or the height, in the click event).
4. Change `default_views` to take what a GPU view needs, and make `with_views` a real method.
5. Put the scene into its own module that the MCP tool can use (section 4), because houses are what the AI will want to look at.

## 6. When to switch the backend

**At the start of the houses plan, not before.** The switch is cheap (one feature, two options, +40 crates, +7 MB, `deny`
passes, the tests do not change), and the seam holds, so there is nothing to find out any more. But until the first 3D view is
written the merged code has nothing that needs wgpu, and the cost is a larger binary and a GPU stack that `naves build`
users do not need. Keeping glow until then also keeps this plan's code, which does not depend on either, simple to review.

The branch `spike/3d-view` can be deleted once the maintainer has read this note; the houses plan starts from this note,
not from the branch (the spike takes shortcuts: CPU compositing of the picture, a fixed mesh size, no per-layer textures).
